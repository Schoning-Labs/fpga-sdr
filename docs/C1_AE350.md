# WP C1: `tr-ae350` — AE350 platform crate

This is a design note from the build-up of the radio, so the numbers and plans in it may predate later changes (the DDR3 speed and the video mode, for example, are not what they were when most of these notes were written), and [docs/learn/HISTORY.md](learn/HISTORY.md) gives the current picture.

What `fw/tr-ae350` implements (docs/PLAN.md WP C1) and, for every register fact it depends on,
exactly where that fact comes from. Checked 2026-09-25. Follows BOARD.md's convention: anything
this crate relies on that is not actually stated in a Gowin/Andes document is marked **NOT
VERIFIED** and listed again in [Unverified facts](#unverified-facts-confirm-on-the-board).

## What was built

`fw/tr-ae350`: start-up (via `riscv-rt`), trap/exception handling, a PLIC driver, the machine
timer, a 16550-compatible UART driver, Andes CCTL cache operations, FPU enable, and two linker
scripts (`memory-ae350.x`, `memory-qemu.x`) implementing docs/ARCHITECTURE.md section 5.4's memory
map. `fw/tr-app/src/bin/qemu_smoke.rs`: the QEMU-only test binary. `tools/qemu_c1.sh`: builds and
runs it, hooked into `tools/check.sh`.

Board selection is a Cargo feature (`board-ae350`, default; `board-qemu`), not a runtime switch --
see `fw/tr-ae350/src/board.rs`, which is the one file every address in this crate is read from.

## Start-up: `riscv-rt`, not hand-written

docs/ARCHITECTURE.md section 5.2 already recorded `tr-ae350`'s start-up as `riscv-rt` before this
WP began; this keeps that choice rather than reopening it, and the reasoning holds up:

- The reset sequence a bare-metal RV32 image needs -- clear `.bss`, copy `.data` from its load
  address, set up the stack pointer, install a trap vector, then jump to `main` -- is the same
  sequence on every RV32IMAFC target and is exactly what `riscv-rt` does. Hand-writing it saves
  one crate dependency and gains nothing: the AE350 has no start-up step outside that sequence
  (no clock tree to program before DDR3 is usable in the `BUILD_LOAD` boot mode this WP uses --
  GDB/eBIOS loads the image into already-running DDR3, MUG1029 table 5-1).
- `riscv-rt` 0.18's `#[exception(...)]` / `#[core_interrupt(...)]` attributes, keyed off
  `riscv::interrupt::{Exception, Interrupt}` (standard RISC-V trap causes, RISCV-PRIV), give
  every exception and the two local interrupts (machine timer, machine software) a named, typed
  handler instead of hand-decoding `mcause` in one big trap function. What is AE350-specific
  (the PLIC, the timer's actual addresses) is not part of `riscv-rt` at all -- this crate's own
  `plic.rs` / `timer.rs` supply that, matching docs/ARCHITECTURE.md 5.2's line for `tr-ae350`
  ("start-up (riscv-rt), traps, PLIC, machine timer, UART...").
- `single-hart` feature: MUG1031 3.1 confirms one Andes A25 core, no SMP, so none of
  `riscv-rt`'s multi-hart machinery (`_mp_hook`, per-hart stacks) is needed.
- Cost: `riscv-rt`'s linker-script conventions (`REGION_TEXT`/`REGION_DATA`/... aliases,
  `_stack_start`, `_heap_size`) have to be followed exactly, which is why `memory-ae350.x` and
  `memory-qemu.x` look the way they do (see below) -- documented in the crate's own source
  (`riscv-rt` docs.rs page) and matched here.
- Exception/interrupt handlers themselves (`#[exception(...)]`, `#[core_interrupt(...)]`) live in
  the binary crate (`fw/tr-app/src/bin/qemu_smoke.rs` for this WP), not in `tr-ae350` -- they are
  per-binary by construction (one handler per linked image), so a library crate cannot usefully
  define the real firmware's handlers ahead of time.

## Interrupts

MUG1029 chapter 4:

- Table 4-1: local interrupts handled directly by the core -- `nmi` (WDT), `mtip` (machine timer),
  `msip` (machine software), plus PLIC-arbitrated `meip`/`seip`. Confirms the machine timer
  interrupt is *not* a PLIC source (it is the RISC-V-standard local `mtip`/`mie.MTIE` path), which
  is why `timer.rs`'s doc comment says the QEMU smoke test's timer interrupt "does not go through
  the PLIC".
- Table 4-2: PLIC source numbers. Source 1 = RTC period, 2 = RTC alarm, 3 = PIT, **4 = GP0**, 5 =
  SPI2, 6 = I2C, 7 = GPIO, 8 = UART1, **9 = UART2**, 10 = DMAC, **11-25 = GP1-GP15**, 26 = SMU
  standby, 27 = SMU wakeup. This is where ARCHITECTURE.md section 4.3's "16 fabric lines GP0-GP15
  into the PLIC" land in PLIC source-number space; `tr-fabric` (WP C3) will need this table, not
  just `tr-ae350`.
- MUG1031 3.1: "Configurable number of interrupts: 1-1023", "Number of interrupt priorities: 15",
  "Configurable number of targets: 1-16", "Vectored PLIC extension", "Support software
  interrupts", "Support 16 user interrupts" -- confirms the PLIC's field widths (which is why
  `plic.rs`'s standard-layout assumption is plausible) but, like MUG1029, never gives the
  register byte offsets themselves (see [Unverified facts](#unverified-facts-confirm-on-the-board)).

## Cache (CCTL)

MUG1029 chapter 6:

- Table 6-1/6-2: both L1 caches are 32 KB, 4-way, 32-byte lines, LRU -- `cctl.rs`'s
  `DCACHE_LINE = 32` constant.
- Table 6-3: Cache Control Register bit layout -- `IC_EN` bit 0, `DC_EN` bit 1, `IC_ECCEN` bits
  [3:2], `DC_ECCEN` bits [5:4], `EC_RWECC` bit 6, `DC_RWECC` bit 7, `IC_FIRST_WORLD` (fill policy,
  read-only) bit 8, `CCTL_SUEN` (S/U-mode CCTL access enable) bit 11. `cctl.rs::enable_caches()`
  only sets `IC_EN`/`DC_EN`; the ECC and S/U-mode bits are left at their reset value (0) since
  nothing in this WP needs them yet.
- Table 6-4: CCTL command encoding. Used here: 0 = `L1D_VA_INVAL`, 1 = `L1D_VA_WB`, 6 =
  `L1D_WBINVAL_ALL`, 7 = `L1D_WB_ALL`, 23 = `L1D_INVAL_ALL`. These specific two (`L1D_VA_INVAL`,
  `L1D_VA_WB`) are the ones ARCHITECTURE.md section 4.2 names for keeping fabric-shared DDR3 rings
  coherent by software.

**Not exercised under QEMU**: QEMU's `virt` machine uses a generic RV32 CPU model with no Andes
custom CSRs at all; any CCTL instruction would itself trap as illegal there. `cctl.rs` only
compiles under `board-ae350` (see its module doc). This is the one C1 deliverable that genuinely
cannot be verified before the board, matching PLAN.md's own framing of WP C1's done-test (QEMU
covers "the target-independent parts"; cache control is not one of them).

## UART2

MUG1029 chapter 7. 7.1.1: "Programmable timing compatible with 16C550A UART" -- the reason one
generic driver (`uart.rs`) can drive both boards. Register offsets, read from the prose register
headers (not the reflowed Table 7-1, whose columns pdftotext scrambled on extraction -- the
per-register prose headings a few paragraphs later in the same chapter were unambiguous and are
what `board.rs`'s doc comments cite):

| Offset | Register | Notes |
|---|---|---|
| 0x00 | ID/Revision | not used |
| 0x10 | Hardware Configuration | FIFO depth; not used |
| 0x14 | Over Sample Control (OSC) | reset value 0x10 (16x oversample); left at reset, see baud note below |
| 0x20 | RBR (read) / THR (write) / DLL (DLAB=1) | |
| 0x24 | IER (DLAB=0) / DLM (DLAB=1) | |
| 0x28 | IIR (read) / FCR (write) | |
| 0x2C | LCR | |
| 0x30 | MCR | not used (no modem lines wired to a console UART) |
| 0x34 | LSR | |
| 0x38 | MSR | not used |

A constant 4-byte stride from 0x20 to 0x38 -- `board::ae350::UART.stride = 4`. LSR bit layout
(Table 7-18: `ERRF`7 `TEMT`6 `THRE`5 `LBreak`4 `FE`3 `PE`2 `OE`1 `DR`0) is bit-for-bit the classic
16450/16550 LSR, confirming `uart.rs` can share its `LSR_DR`/`LSR_THRE` constants with the QEMU
ns16550a backend (stride 1 there instead of 4, QEMU-SRC `hw/riscv/virt.c` `VIRT_UART0` /
ns16550a's fixed reg-shift-0 layout).

**Baud-rate formula NOT VERIFIED**: MUG1029 documents the Divisor Latch and OSC registers but the
downloaded text never states the equation relating `uclk`, the divisor, and OSC to the resulting
baud rate, nor UART2's actual `uclk` source frequency on this board. `uart.rs::init()` uses the
classic 16550 relationship (`baud = uclk / (divisor * oversample)`) with OSC left at its reset
value (16x) and documents this as unverified; confirm against a real terminal once UART2 is wired
up (PLAN WP B3).

## Machine timer (PLMT)

MUG1029 chapter 15. Table 15-1: `mtime` lo/hi at PLMT-base +0x00/+0x04; `mtimecmp0` (hart 0)
lo/hi at +0x08/+0x0C. Table 15-2/15-3: a timer interrupt fires while `mtime >= mtimecmp`, and
writing `mtimecmp` de-asserts it -- both standard RISC-V behaviour (RISCV-PRIV), confirmed
restated for this chip. `timer.rs`'s AE350 backend is a direct transcription of these four
offsets.

**mtime_clk frequency NOT VERIFIED**: MUG1029 15.1.2 only says the clock "can work at any
frequency" and "in most cases... share[s] the same clock source as the RTC clock"; no value is
given anywhere BOARD.md cites. `board::ae350::TIMER_HZ` is a placeholder (`clk_ahb`, the nearest
documented clock from ARCHITECTURE.md section 2; 80 MHz since 2026-10-13. If the timer shares the RTC source as
MUG1029 says is usual, its rate is the RTC clock, 10 MHz: the ladder program prints the rate it counts). Nothing in `timer.rs`'s logic depends on this
being right -- `arm_after()` takes a tick count, not a time -- only a real duration written from
this constant would be wrong until it is confirmed.

## FPU enable

`mstatus.FS` (RISC-V privileged spec, not AE350-specific) -- `fpu.rs` sets it to `Initial`
(`0b01`) via a raw `csrs mstatus, ...`. MUG1031 3.1 confirms the core implements F and D; this
crate's target (`riscv32imafc-unknown-none-elf`) only emits F (BOARD.md "Rust target": no
upstream RV32 target enables D). Verified under QEMU (its `virt` CPU implements F/D).

## PLIC register layout

`plic.rs` implements the standard RISC-V PLIC memory layout (priority array, pending/enable
bitmaps, per-context threshold and claim/complete). **NOT VERIFIED for the AE350**: neither
MUG1029 nor MUG1031 spells out this byte layout anywhere (MUG1031 8.2.1's "PLIC Configuration" is
a screenshot-driven guide to the Gowin IDE's IP configuration GUI, not a register reference).
MUG1031 3.1's field-width list (1-1023 sources, 15 priorities, 1-16 targets) is consistent with
the standard layout but does not prove it. This is the standard layout used by essentially every
public Andes AE350 BSP and is exactly what QEMU's `virt` PLIC implements (QEMU-SRC), so the QEMU
half of this crate genuinely exercises the same code path -- but on real hardware, confirm before
trusting a claim/complete round trip (PLAN WP B3): `plic.rs`'s `priority()` readback, used by
`qemu_smoke.rs`, is exactly the kind of check to repeat first on the board.

PLIC context numbering (which context is hart 0's M-mode target) is likewise assumed, not stated,
for the AE350; on QEMU it is confirmed (QEMU numbers M-mode before S-mode per hart, and this
binary never enters S-mode, so context 0 is right and the smoke test's PLIC writes succeed).

## Andes custom CSRs (cache control)

`cctl.rs` writes `mcache_ctl` (0x7CA), `mcctlbeginaddr` (0x7CB), `mcctlcommand` (0x7CC). These
numbers are **not in MUG1029 or MUG1031** -- both documents describe the *meaning* of the Cache
Control Register and the CCTL commands (chapter 6) but never give a CSR address for either. The
numbers used here come from ANDES-CSR (public Andes AndeStar V5 platform code). Confirm on the
board before trusting any cache-related behaviour: MUG1029 27.18's own reference application
prints `MICM_CFG`/`MDCM_CFG` (a *different*, but related, pair of Andes custom CSRs) as a basic
"can we talk to Andes CSRs at all" sanity check -- worth repeating for `mcache_ctl` specifically
before relying on `enable_caches()`.

## What ran under QEMU vs. what did not

`tools/qemu_c1.sh` builds `fw/tr-app`'s `qemu_smoke` binary (`--features board-qemu`) and runs it
under `qemu-system-riscv32 -M virt -bios none`. Confirmed, every run:

- **UART**: `init()` (FIFO enable/reset, divisor-latch programming, LCR 8N1) followed by polled
  writes -- "hello ok" printed and captured.
- **FPU**: `mstatus.FS` enable followed by an actual `f32` multiply -- "fpu ok" printed with the
  correct product, and the process does not trap.
- **PLIC**: a priority register write followed by a readback of the same value, plus a threshold
  write -- "plic ok" printed with the readback matching what was written.
- **Machine timer interrupt**: `timer::arm_after()` plus `mie.MTIE`/`mstatus.MIE` enable, then a
  `wfi` loop until a real `#[core_interrupt(Interrupt::MachineTimer)]` handler runs, disarms the
  timer, and sets a flag -- "timer ok" printed from inside the handler.
- **Illegal-instruction trap**: a deliberate all-zero-word instruction, caught by
  `#[exception(Exception::IllegalInstruction)]`, which reads back `mcause` (`0x2`, matching
  RISCV-PRIV's Illegal Instruction cause code) and `mepc` -- "trap ok" printed with both values,
  then a clean QEMU shutdown via the test finisher.

**Not run anywhere yet** (real hardware only, PLAN WP B3): CCTL cache operations (`cctl.rs`,
compiled out under `board-qemu`); anything about the real UART2 baud rate, the real PLIC register
layout, or the real machine-timer frequency, all listed above.

## WP C4: FP registers and traps

Not part of WP C1 itself; recorded here because it changes `fw/tr-ae350` (`fpu.rs`) and depends on
everything above (traps, the machine timer, `+d`). Checked 2026-09-25.

### The problem

`riscv-rt`'s trap entry (start-up crate, see "Start-up" above) saves only the integer registers on
every trap. `fw/.cargo/config.toml` builds this workspace with `-C target-feature=+d` so `f64`
runs on the A25's hardware double-precision unit (`docs/CPU_BUDGET.md` section 4, point 7: 3.3x
fewer instructions on FT8 decode) -- which makes every FP register 64 bits wide. If any interrupt
handler executed a floating-point instruction, it would silently overwrite whatever value the task
it interrupted had live in that register, with no saved copy anywhere to restore from
(`docs/CPU_BUDGET.md` section 7 first surfaced this as a finding of the cpu-budget work, not
caused by it). This is PLAN WP C4.

### Decision: forbid FP in interrupt handlers, not save/restore it -- enforced automatically at the trap entry, not by handler convention

ARCHITECTURE.md section 5.3 already never puts FP work at interrupt level, for every handler this
firmware actually has:

- Back-end audio interrupt (line 10, every 128 samples at 12 ksps): wakes the noise-reduction task;
  the FP-heavy NR work runs in that task, not the handler.
- IQ-block interrupt (line 2): "bounded work, measured with `mcycle`" -- integer ring/index
  bookkeeping, not demodulation (that moved to the FPGA in the cpu-budget work, 3.10-3.11).
- 25 ms timer interrupt: HL2 TX lease renewal, watchdog, safety checks -- all integer/control flow.

So no handler in this firmware's design needs the FPU. Saving and restoring the caller-saved FP
registers (`ft0`-`ft7`, `fa0`-`fa7`, `ft8`-`ft11` = 20 registers; the callee-saved ones, `fs0`-
`fs11`, are the handler function's own prologue/epilogue's problem, same as for the integer
registers `riscv-rt` already handles this way) on every trap would pay a real cost -- 20 `fsd` +
20 `fld`, 40 FP load/store instructions -- forever, on every interrupt, to guard against a case
that structurally never happens here. A lazy save keyed on `mstatus.FS`'s dirty bit does not help:
that bit is a coarse per-hart "has any FP register been written since it was last clean" flag, not
a record of which specific registers the interrupted code had live, so it cannot tell a handler's
FP write from the interrupted task's own -- it does not make save/restore safe to skip, only
sometimes cheaper when it would already have been safe to skip.

**First version (superseded)**: an opt-in `ForbidFpGuard` that every `#[core_interrupt(...)]`/
`#[exception(...)]` handler had to open by hand as its first statement, forcing `mstatus.FS` = Off
for its scope. Review caught the flaw: opt-in means a future handler that forgets to open it
silently reintroduces the exact corruption this WP exists to prevent, with nothing to catch the
mistake until it happened on real hardware.

**Chosen instead, final**: `fw/tr-ae350/src/trap.rs` overrides `_start_trap` itself -- the single
assembly routine every trap in this firmware goes through (`riscv-rt`'s `link.x.in` `PROVIDE`s
`_start_trap = _default_start_trap` only if the final binary does not define `_start_trap` itself;
this crate now does). This workspace does not enable `riscv-rt`'s `v-trap` feature (`fw/tr-app/
Cargo.toml`: only `single-hart`), so `riscv-rt` runs in direct/non-vectored mode, where *every*
trap -- every interrupt and every exception -- lands at this one entry point and is dispatched to
`_start_trap_rust`, which reads `mcause` and calls the right handler. `_start_trap` forces
`mstatus.FS` = Off before calling into `_start_trap_rust` (so before any handler runs) and restores
the pre-trap FS value after it returns (so before `mret`), for every trap, unconditionally. No
handler can opt out, forget, or bypass this short of not using `riscv-rt`'s trap mechanism at all --
not something a handler author does by accident. With FS forced Off, any F/D instruction a handler
executes -- including one a library emits without the author intending it, e.g. an `f32`/`f64` in a
`Debug`/`Display` formatter -- traps immediately as Illegal Instruction instead of running and
clobbering a register. That trap is the enforcement PLAN WP C4 asked for ("enforced by a check"): a
real hardware fault on the first violation, not a lint that can be missed, a convention that erodes
over time, or a guard call a handler author forgets to add.

**Why FS needs an explicit save/restore, not just "force it off"**: `mret` only swaps
`mstatus.MIE`/`MPIE`/`MPP` automatically (RISC-V privileged spec); `FS` is untouched by a trap
return. Forcing FS = Off on entry and leaving it there would resume the interrupted task with
FS = Off even if it had FP work in flight (Initial/Clean/Dirty) before the trap, so its very next
FP instruction would spuriously trap. `trap.rs`'s `_start_trap` therefore saves the FS bits to an
extra stack slot (one word larger than `riscv-rt`'s default 16-word integer trap frame, kept
16-byte aligned) before forcing FS off, and restores from that slot after `_start_trap_rust`
returns, before the integer registers are reloaded and before `mret` -- covering an interrupt
handler and an exception handler identically, since `#[exception(...)]` handlers may return `()`
(not just `!`) and fall through this same shared restore path.

**Cost per interrupt**: six extra integer instructions versus `riscv-rt`'s stock
`_default_start_trap` (entry: load the FS mask, read+mask+store `mstatus`, clear FS; exit: reload
the mask, clear+set `mstatus` from the saved value), plus one extra 4-byte stack slot (padded to 16
bytes for alignment). No FP register is read or written -- against the ~40 FP load/store
instructions a full caller-saved-register save/restore would cost unconditionally on every
interrupt. Not separately measured under QEMU (QEMU's functional CPU model does not model
instruction timing); `docs/CPU_BUDGET.md` section 6's budget already has slack here since neither
the C1 nor C4 trap paths were counted as a cost line, and six integer instructions per interrupt is
negligible next to the workload already budgeted for the handlers that actually run (2 ms-10.7 ms
periods; measure alongside PLAN WP B8's `mcycle`/`minstret` work if it ever needs a number).

### Done-test: `fw/tr-app/src/bin/qemu_c4.rs`, run by `tools/qemu_c4.sh` (hooked into `tools/check.sh`)

One QEMU run, four phases:

1. `baseline`: an f64 logistic-map loop (`x' = 3.999999 * x * (1 - x)`, chaotic regime -- any
   single wrong bit diverges the whole trajectory rather than nudging the last digit, which is
   what makes bit-for-bit equality a meaningful check and not a coincidence of rounding), no trap
   of any kind fires during it.
2. `with_interrupts`: the identical loop, with a real `#[core_interrupt(Interrupt::MachineTimer)]`
   handler re-arming itself every 2 ms and firing throughout the loop (470-580 times across several
   runs -- QEMU's `virt` timer ticks against wall-clock time like `tools/qemu_c1.sh`'s does, so the
   exact count varies with host load; the test asserts it is at least 10, i.e. that interrupts
   genuinely fired repeatedly). The handler does only integer work (re-arm, counter increment) and
   opens no guard of any kind -- `_start_trap` has already forced FS off before it started running.
   Compared bit for bit (`f64::to_bits()`) against `baseline`; prints "bitidentical ok".
3. `with_exceptions`: the identical loop again, with a deliberate `ebreak` (`Exception::Breakpoint`,
   the raw 4-byte encoding, not left to the assembler's choice) executed every 20,000 iterations
   (200 firings total, deterministic every run since this is a synchronous exception, not tied to
   wall-clock time unlike the timer). The handler advances `mepc` past the `ebreak` and returns
   normally, so `_start_trap` falls through the same FS-restore-then-`mret` path an interrupt
   handler's normal return uses. Compared bit for bit against `baseline`; prints
   "exceptionbitidentical ok" -- this is the check that FS survives an *exception*, not just an
   interrupt, confirming the trap-entry fix covers both trap kinds through the single shared entry
   point rather than only the case originally measured.
4. `guard`: one more timer interrupt, this time with the handler deliberately executing
   `fadd.d fa0, fa0, fa0`, with no handler-side guard call at all. It traps as Illegal Instruction
   before the instruction can run (confirmed by `mcause = 0x2`, RISCV-PRIV's Illegal Instruction
   cause code); the exception handler reports it and exits -- "guard ok". Run several times: always
   caught, never silently executes -- proving the protection cannot be skipped by a handler simply
   omitting a call, because there is no call to omit any more.

Confirmed, every run: "bitidentical ok", "exceptionbitidentical ok" and "guard ok" all print, and
`tools/qemu_c1.sh` (the original C1 smoke test: UART, FPU enable, PLIC, a real timer interrupt, an
illegal-instruction trap) still passes unchanged with the new shared `_start_trap` in place --
`tools/qemu_c4.sh` fails loudly (missing expected output, `timeout`-bounded) if any of its own
checks does not print.
